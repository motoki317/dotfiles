# 日本語の表記規範

出典：<https://gist.github.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d>（抜粋して再構成）、<https://github.com/nanaism/yomiyasu>（MIT、`$HOME/.claude/skills/tech-writing/LICENSE-yomiyasu`）

## 整形

- 一文ごとに改行する。段落の区切りは空行で示す。
- コード、差分、ログ、設定ファイルの断片はコードブロックで示す。
- ダッシュ（emダッシュ`—`、horizontal bar`―`、いわゆる2倍ダッシュ「——」）を日本語の地の文と見出しで使わない。同格や補足の挿入（「A——挿入——B」）は括弧（）に、言い換えや敷衍（「A——B」）は句点で二文に分けるか読点でつなぐ。範囲を示すenダッシュ`–`、英語の複合語（`Curry–Howard`など）、コードブロック、書誌情報は対象外。
- 中黒（・）を日本語の並列で使わない。ただし単一の固有名詞の内部では使ってよい。
- 和文と英単語、略語、数字のあいだに半角空白を入れない（「このREADMEは」「HTTPステータス」）。コードスパンの前後は対象外。英文の中に日本語の語を置くときは、英文の語の区切りに従う。
- 箇条書きの前置き、見出しの末尾、文末にコロン（「：」「:」）を置かない。「次の3点です。」のように句点で閉じる。
- 用語とその定義（その語が何を指すか）を並べる箇条書きは、区切り線ではなく全角コロンで「**用語**：説明」と書く。このコロンは文中にあるので、前項の対象外。
- 文体（ですます調、である調）を文書内で混ぜない。既存の文書やリポジトリの文体に合わせる。手がかりがなければ、技術記事はですます調で書き、論文調の「本稿では」「筆者は」を使わない。

## 文の長さと読点

- 一文は平均30〜45字を目安にする。60字を超える文は、節の切れ目で二文に分ける。コードスパン、URL、「」で囲んだ部分は、それぞれ1字と数え、中の読点も数えない。
- 10字未満の短文を続けて並べない。
- 読点は一文に二つまで（列挙の読点は数えない）。文頭の目的語の直後に、強調のための読点を打たない（「前提を、経路が添える」）。
- 同じ文末（です、ます、でした、ました、である、だ）を3文続けない。
- 漢語が続く箇所は、動詞や和語に開く。サ変名詞を「の」で何段もつないだ名詞句は、動詞を使った文に書き直す（「保守性担保機能の形骸化の防止。」→「保守性を保つ仕組みが形骸化しないようにする。」）。

## LLM口調（禁止リスト）

書き上げたら点検する。
書いている文書の中で定義した術語として使う語は対象外。

- 予告と総括：「重要なのは〜である」「結論から言うと」「正直に言うと」「避けたいのは」「ここで注目すべきは」「本章では〜を扱う／探求する」「ここでは〜について見ていく」「まとめると」「要するに」（直前の言い換えだけのとき）、「〜に他ならない」「〜というわけです」「面白いのはここです」
- 定型の結び：「いかがでしたでしょうか」「ぜひ試してみてください」「〜の参考になれば幸いです」、読後の効果の約束（「これを理解すれば業務効率が飛躍的に向上します」）、短い記事の「まとめ」見出し、本文が支えない教訓や社会への提言で終わる段落
- 一般論の前置き：「一般に〜」「多くの人が〜」「現代社会において〜」「近年、〜の発展は目覚ましく」「もちろん〜とは限らないが」（本題の前に置くとき。読者の経験に訴える根拠はmanuscript.mdに従う）
- 正面から系：「正面から扱う」「正面から回収する」「正面から見る／書く／立てる」（中身の代わりに姿勢だけを宣言する）
- 空虚な形容：「不可欠」「核心的」「鍵となる」「根本的な」（主張の中身を説明せず強調だけする）、「多角的」「包括的」「総合的」（何をどう見たかを書かない）
- 壮大化：「真理」「真実」「結末」「宿命」「運命」「境地」「極致」「究極」「虚飾」「虚像」「美学」「深淵」「禁欲的」「優美」「冷徹」「残酷」「凝縮」「結晶」（小さな体験や日常の判断を大げさに語る）
- 質感や理解を装う語：「手触り」「肌感」「肌感覚」「体温」「温度感」「熱量」「血の通った」「泥臭い」、「解像度（を上げる）」「腹落ち」「メンタルモデル」「文脈」、「本質（的）」「地に足のついた」「等身大」、「営み」「羅針盤」「起爆剤」「触媒」、「意思決定OS」のような定義のない造語（何をどこまで調べ、何を測ったかを書く）
- 空虚な動詞：「掘り下げる」「深掘りする」「言語化する」（何をどう書いたかを示さず終わる）、「触れる」「言及する」（一段落で済ませるだけ）
- 接続の型：「〜において」「〜という側面から」「〜の観点から」（新情報なし）、「さらに」「また」「加えて」の連打
- 曖昧な条件：「適宜」「必要に応じて」（条件と結果を書く）
- 弱い緩和と空虚な強調：「〜と言えるだろう」「〜かもしれない」（根拠なく主張を弱める場合だけ。推量、仮定、読者の疑念、作中人物の認識、体験談での書き手自身の感想なら残す）、「非常に」「極めて」「大いに」（中身のない強調）

悪い例：「本章では、〇〇の理論を正面から扱う」「この前提を、ここで正面から回収する」「多角的に分析すると、重要なのは〜である」。
直し方：悪い例の一つめと二つめは文ごと削り、理論や前提の中身から書き始める。
三つめは「正しさを誰が知っているかで、評価が決まる」と書く。

## 比喩動詞と英語直訳調

SKILL.md「Sentence devices」の比喩動詞の日本語リスト。
概念、方針、時間を主語や目的語にとるときだけ違反になる。
文字どおりの対象をとる用法や定着した慣用句（「お腹を壊す」「氷を溶かす」「主導権を握る」「過労で卒倒する」）は対象外。
書き換えるときは語を差し替えず、読者が観察できる操作や状態変化を書く。

| 語 | 典型（英語の元の表現） | 書き換えの方向 |
|---|---|---|
| 効く、効いてくる | 「地味に効きます」 | 何を防ぐか、何が速くなるか（「重複登録を防げる」） |
| 壊れる、静かに壊れる | 「もう片方が壊れる」（silently fail） | 「要件を満たせなくなる」「例外が出る」「エラーを出さずに失敗する」 |
| 倒す | 「残さない側に倒す」 | 「原則として除外する」「〜を採用する」 |
| 溶かす | 「時間を溶かした」 | 何にどれだけ時間がかかったかを書く |
| 潰す | 「1つずつ潰していく」 | 「エラーを1件ずつ解消する」「原因を1つずつ検証する」 |
| 踏み込む | 「〜まで踏み込んで」 | 「内部実装まで調べて」 |
| 引き返す | 「動かしながら引き返す」 | 「元の状態に戻す」「ロールバックする」 |
| 添える | 「経路が代わりに添える」 | 「参照する」「付与する」「渡す」 |
| 収斂する | 「その価格帯に収斂した」 | 「〜に決まった」 |
| 沈黙する、黙って | 「黙って捨てられる」（silently ignored） | 「通知なく破棄される」「ログを出さずにスキップする」 |
| 〜した瞬間 | （the moment …） | 「〜した直後に」「〜した時点で」 |
| 正本 | （single source of truth） | 「信頼できる唯一の情報源」「マスターデータ」 |
| 〜を指している | （point to / suggest） | 「〜を表している」「〜と考えられる」 |
| 耐力のある、構造を支える | （load-bearing） | 「外せない」「それがないと成り立たない」 |
| 深く分け入る | （delve into） | 「詳しく調べる」 |

## 要点検の語

AI普及後の技術記事で急増した語。
普通の技術用語でもあるので、括弧内の典型のように比喩や定型として使っているときだけ書き換える。

- 障害の比喩：「事故」「混ざる」「落とし穴」「破綻」「実害」「素通り」（「〜という事故」「落とし穴があります」→「不整合」「例外が発生する」「考慮すべき点」）
- 確認の比喩：「実測」「疑う」「照合」「突き合わせる」「断定」「取り違える」（「実測では」「〜を取り違えると」→「計測値では」「確認する」「比較して検証する」）
- 役割や位置の比喩：「入口」「土台」「道具」「核心」「主役」「構図」「線引き」（「〜の入口として」「〜するための土台」→「導入として」「前提条件」「基礎知識」）
- 評価の定型：「既定」「別物」「定番」「要点」「定石」「桁違い」（「既定では」「〜とは別物です」→「初期設定では」「性質が異なります」）

## 例（SKILL.mdの各装置の日本語形）

- **腑分け**（lump禁止）：相互依存する三つの未決事項を「同じ決定を別々に下していた」とくくらない。「どれも別々の決定であり、しかも互いに依存している」と腑分けする。
- **機構の明示**（causality）：「手順で分けると変更が全体に波及する」ではなく「各工程がデータを受け渡すための表現を共有してしまい、その表現を変えると全体に波及する」。
- **条件付きの正確さ**（no absolute guarantees）：「必ず検出できる」ではなく「〜が成り立つときに限り検出できる」。
- **並列の統合**（merge parallel facts）：同じ論理的役割の事実は一文にまとめ、論理的地位を文頭の語で示す（「当然、経理部の月次処理も顧客の支払いも〜」）。
- **強い言い切り**（grounded claims）：本文内の根拠で命題が確定しているなら、「〜も一案である」のようなためらいのある述語で薄めず、根拠が支える強さで言い切る（「〜が必須である」）。要件と警告の強さも弱めない。
- **動作主**（actor）：「片方だけを見ると、もう片方が壊れる」の「片方」は、文脈から特定できる名詞に戻す（「開発速度だけを基準にすると、保守性の要件を満たせなくなる」）。
- **要請と能力**（procedural vs capability）：読者にしてほしい操作は「〜してください」、システムの機能は「〜できます」と書く。主語のない「〜します」では、読者の操作かシステムの動作かがわからない。「引数を渡して実行します」は、指示なら「引数を渡して実行してください」、機能の説明なら「引数を渡して実行できます」にする。要請に過剰な敬語の前置きを重ねない。

## 点検（機械的）

まず`python3 $HOME/.claude/skills/tech-writing/scripts/yomiyasu_lint.py <ファイル>`で行単位の候補を出す。
100点満点のスコアは使わない。
規範や手順を並べる文書では、太字と箇条書きの比率の警告は対象外。
リンターはダッシュ、中黒、文の長さ、読点の数、一文一行を検査しない。
見出し、表、引用ブロック（`>`）の行は語彙も検査しない。
そこで次の項目は、コードブロックの外で手でも検索する。
該当箇所は書き直す前に分類する。
推量、仮定、読者の疑念を表す語や、文字どおりの用法は違反ではない。
リンターが挙げる「装置」はこの規範の術語である。

- ダッシュ類（`—`、`―`、`——`）、並列の中黒（・）
- 和文と英数字のあいだの半角空白、行末のコロン、絵文字
- 行頭の`- **`：見出し語が定義される用語でなければ、太字を外す（SKILL.md「Format」）
- LLM口調リスト、比喩動詞の表、要点検の語
- 「ではなく」「だけでなく」「わけではない」：読者が抱いていない誤解を否定していないか
- 「かもしれない」「だろう」「ようだ」「らしい」：根拠なく主張を弱めている場合だけ削る
- 60字を超える文、読点が三つ以上ある文、3文続く同じ文末
- 一文ごとに改行されていない段落
